# The kit on Codex CLI

`dist/codex/` is generated by `devil export codex` from the kit's Claude-format
sources. Never edit it: `bash tools/export.sh --check codex` regenerates into a temp
directory and fails on any difference, and CI runs it.

Measured against Codex CLI **0.159.2** (`@openai/codex`) on 2026-09-30, inside a
`node:22-slim` container with `HOME` redirected, because the CLI is not installed on
the host. Every claim below is in `doc/HARNESSES.md`, section "codex, measured for
X4", with the command that produced it and the output it produced. A row that says
UNVERIFIED is a row that was not measured.

## Install

`$KIT` below is the absolute path of the kit checkout: the directory holding `bin/`,
`hooks/`, `rules/` and `skills/`.

Two routes, both measured. Pick by how much of the kit you want.

### Route 1: install the kit itself (measured, everything works)

Codex reads a Claude-compatible plugin root as it stands, so this route generates
nothing and needs no file from this directory:

```sh
codex plugin marketplace add /absolute/path/to/claude-deal-with-the-devil
codex plugin add devil@univers42
codex plugin list        # devil@univers42  installed, enabled  <version>
```

A local path works as a marketplace source here. The same call on Copilot CLI 1.0.59
parsed a relative path as a GitHub shorthand and failed, so this is Codex-specific, not
a property of local paths.

The version in that line is read from `.claude-plugin/plugin.json`, and the installed
copy lands in `~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/`. Codex also
advertises each of the plugin's skills to the model as `devil:<name>`, and it rewrites
the plugin's `commands/*.md` into skills of its own. It finds `hooks/hooks.json` in the
plugin root by default and sets both `PLUGIN_ROOT` and `CLAUDE_PLUGIN_ROOT` for the hook
scripts, so `hooks/scripts/hooks.py` runs unchanged.

The cost is the whole repository in the cache, `dist/` and `tests/` included. That is
the price of route 1, and it is why route 2 exists.

### Route 2: install this directory as a portable plugin

This directory is an Agent Plugins 1.0 package: a root `plugin.json`, a `hooks/`
directory and the always-on rules. Codex installs it like any other plugin, from a
marketplace that points at it.

```sh
KIT=/absolute/path/to/claude-deal-with-the-devil
HOST=/absolute/path/to/your/project

# The plugin root must contain hooks/scripts/ for the hook command to resolve,
# because Codex copies the plugin into its own cache and expands PLUGIN_ROOT there.
ln -sfn "$KIT/hooks/scripts" "$KIT/dist/codex/hooks/scripts"

mkdir -p "$HOST/.codex/plugins"
cat >"$HOST/.codex/plugins/marketplace.json" <<JSON
{
  "name": "devil-local",
  "interface": { "displayName": "devil (local)" },
  "plugins": [
    {
      "name": "devil",
      "source": { "source": "local", "path": "$KIT/dist/codex" },
      "policy": { "installation": "AVAILABLE", "authentication": "ON_INSTALL" },
      "category": "Productivity"
    }
  ]
}
JSON

codex plugin marketplace add "$HOST/.codex/plugins"
codex plugin add devil@devil-local
```

The symlink is the one step that cannot be generated. Codex installs a plugin by
copying it, so `${PLUGIN_ROOT}` points inside
`~/.codex/plugins/cache/.../devil/<version>/`, never at your checkout, and a hook
command that named an absolute kit path would break the moment the version bumped. A
symlink into the plugin root travels with the copy and resolves there. Route 1 needs
none of this because `hooks/scripts/` is already inside the plugin.

### Always-on rules

Codex reads `AGENTS.md` from the project tree. It does not read one from an installed
plugin: a marker in a plugin-root `AGENTS.md` never reached the model-visible prompt,
the same marker in the project root did. So the rules go in the project:

```sh
ln -sfn "$KIT/dist/codex/AGENTS.md" "$HOST/AGENTS.md"
```

Codex wraps that file in `<INSTRUCTIONS>` inside the first user message of a session,
which is where the twelve rules have to be to be always-on.

### How a host gets the skills

Two ways, and route 1 already does the first.

- **From the plugin.** A plugin's `skills/` is read natively and each skill is
  advertised as `devil:<name>`. Measured on 0.159.2, when the kit had 23 skills: all 23
  appeared in the model-visible skill list, with the plugin prefix. The one migrated command arrives
  as `devil:source-command-compat-audit`, so the count there is 24.
- **From the project.** `<host>/.agents/skills/<name>/SKILL.md` is read, without a
  prefix. That is the portable Agent Skills location, shared with Copilot CLI, and it
  is the route when you want the skills in a project that has no plugin installed:

  ```sh
  mkdir -p "$HOST/.agents/skills"
  for d in "$KIT"/skills/*/; do ln -sfn "$d" "$HOST/.agents/skills/$(basename "$d")"; done
  ```

`.claude/skills` is not a Codex location. The kit's `skills/` is not copied into this
directory for the same reason: it is read where it already is.

## What is degraded

| Gap | Consequence | Why it cannot be fixed here |
|---|---|---|
| Commands | seventeen of eighteen never reach the model | Codex migrates a plugin's commands to skills itself, and the result for this kit is one of eighteen. The generator cannot hand it a different `commands/` tree without second-guessing the harness's own migration |
| A migrated command is a skill, not a slash command | it is invoked by the model, not typed as `/name`, and it carries no `$ARGUMENTS` | the migration writes its own `SKILL.md` with a `## Command Template` section. The command body survives; the invocation does not |
| `disable-model-invocation`, `argument-hint`, `allowed-tools` | dropped | the migrated skill's frontmatter carries `name` and `description` only, which is what the Agent Skills specification asks for |
| Hooks are not trusted on install | nothing the plugin bundles runs until a human opens `/hooks` and trusts the definition | plugin hooks are non-managed hooks, and Codex records trust against the hook's hash, so any edit asks again. `--dangerously-bypass-hook-trust` is the one-shot override |
| `PLUGIN_ROOT` is the installed copy | a hook command naming an absolute checkout path breaks on the next version bump | Codex installs by copying the plugin into its own cache. The README route 2 symlink is the workaround, and it is why the generated command uses the variable |
| `AGENTS.md` in a plugin root is ignored | the rules have to live in the project | measured: the same marker in a project root was injected and in a plugin root was not |
| Path-scoped rule skills | the seven `stage: rule` skills load whenever the model picks them | Codex reads `name` and `description` from a skill; `paths:` has no field to land in |

## What is not supported

- `templates/mcp.json`. A portable plugin declares its own servers in a root
  `mcp.json` (Agent Plugins MCP schema, one `type` per server). The kit ships no MCP
  server of its own, and copying a host's template into a generated plugin would ship
  `npx` servers the host did not ask for. Declare your own.
- Slash commands as such. Codex has no command template format of its own here; what
  it does with `commands/` is the migration above.
- `hooks/hooks.json` file for file. The event names are close to Claude's, but `command`
  plus `args` is Claude's spelling and Codex has only `command`, so the generated file
  folds the two together. It also drops the seventeen events Codex never fires.
- Attribution of a commit, a push or a deploy, which stays a human action whatever the
  harness. The hooks enforce only what `hooks/scripts/risk.py` enforces.

## Verifying an install

Everything below runs without a login:

```sh
codex plugin list
codex debug prompt-input "list your skills" | grep -c 'devil:'
```

The first line proves the plugin is installed and enabled with the expected version.
The second counts the kit's skills in the model-visible prompt: the 22 skills plus
however many commands Codex migrates. It printed 24 on 0.159.2, when the kit had 23
skills (one was the `ponytail` tombstone, removed in 1.1.0) and one migrated command; the
count has not been re-measured since. Proving
that a hook denies a force-push needs a session and a model call, so it is not part of
this check.
