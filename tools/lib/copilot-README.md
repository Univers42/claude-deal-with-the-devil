# The kit on GitHub Copilot CLI

`dist/copilot/` is generated by `devil export copilot` from the kit's Claude-format
sources. Never edit it: `bash tools/export.sh --check copilot` regenerates into a temp
directory and fails on any difference, and CI runs it.

Measured against Copilot CLI **1.0.89** on 2026-09-30. Every claim below is in
`doc/HARNESSES.md`, section "copilot, measured for X2", with the command that produced
it and the output it produced. Nothing here is inferred from documentation alone.

The short version: copilot is the most compatible harness measured so far. It reads
`.claude-plugin/plugin.json`, `skills/`, `agents/` and `commands/` from a plugin as they
are, so this dist is four small files. The three things that had to be generated are
each a measured defect, not a stylistic difference, and they are named in the
"What is generated and why" table below.

## Install

`$KIT` below is the absolute path of the kit checkout: the directory holding `bin/`,
`hooks/`, `rules/` and `skills/`.

```sh
KIT=/path/to/claude-deal-with-the-devil
DIST="$KIT/dist/copilot"

# The three directories copilot already reads, linked rather than copied.
# `hooks` is here because ${CLAUDE_PLUGIN_ROOT} resolves to the DIST, not to the
# kit: without this symlink the hook line points at a hooks/scripts/hooks.py that
# is not there, and python3 says so instead of gating anything.
ln -sfn "$KIT/skills"  "$DIST/skills"
ln -sfn "$KIT/agents"  "$DIST/agents"
ln -sfn "$KIT/hooks"   "$DIST/hooks"

# A plugin cannot ship always-on instructions, so the host gets the rules as a file.
mkdir -p "$HOST/.github"
cp "$DIST/copilot-instructions.md" "$HOST/.github/copilot-instructions.md"
```

Then run copilot with the dist as the plugin. For a persistent install:

```sh
copilot plugin install "$DIST"
```

For development, `--plugin-dir` needs no install and no account:

```sh
copilot --plugin-dir "$DIST"
```

Both were exercised here; `--plugin-dir` is the one the measurements used, and
`copilot plugin install <path>` did not appear in `copilot plugin install --help` for
1.0.89, which documents `plugin@marketplace`, `owner/repo`, `owner/repo:path` and a git
URL but no local path. **UNVERIFIED**: the `plugin install` line above. Test it before
you put it in a host's setup.

Check what loaded, with no account and no model call:

```sh
copilot --plugin-dir "$DIST" plugin list --json      # the plugin and its version
copilot --plugin-dir "$DIST" skill list --json        # every skill, with its path
copilot --plugin-dir "$DIST" instruction list         # the host's instruction files
```

## What is generated and why

| File | Why it is not just the kit's own file |
| --- | --- |
| `plugin.json` | the manifest is the version source, so it is copied from `.claude-plugin/plugin.json` at export time and a bump that is not re-exported fails `--check` |
| `commands/<name>.md` | **10 of the kit's 18 commands do not load unfixed.** A `description:` written as a plain scalar holding `Usage: /devil:bench ...` is a YAML mapping value, and copilot's parser rejects it: `commands/bench.md: failed to parse YAML frontmatter: mapping values are not allowed in this context at line 1 column 108`. The generated form is a folded block |
| `hooks.json` | **the Claude hook shape does not run.** copilot reads `command` as a shell line and ignores `args` entirely, so the kit's `command: python3` + `args: [".../hooks.py"]` invokes `python3` with the event JSON piped to stdin, where it dies: `NameError: name 'false' is not defined`. The generated form is one quoted line, and the kit's `hooks/` is symlinked in because `${CLAUDE_PLUGIN_ROOT}` is the dist |
| `copilot-instructions.md` | a plugin cannot ship instructions at all, so this is a file the host copies. It is generated rather than assembled by hand so the 12 rules come from `rules/` and cannot drift |
| `README.md` | this file |

Everything else is a symlink or nothing. That is the measurement, not a preference.

## Verifying the symlinks

`dist/copilot/` is committed without them, because a symlink into a checkout is a
path that only means something on the machine that made it. Run the install block
above once per checkout; `--check` does not and cannot see them. The acceptance
test in `tests/test_export_copilot.sh` creates them itself when the CLI is
available, which is why it can report "the deny path works" rather than "the file
looks right".

## What is degraded

| Gap | Consequence | Measured, and why it cannot be fixed here |
| --- | --- | --- |
| `paths:` on a skill | the 7 `stage: rule` skills (`refactor-c`, `refactor-go`, `refactor-rust`, `refactor-typescript`, `refactor-shell`, `api-convention`, `script-library`) are advertised whether or not a matching file exists. A host pays their descriptions in every session and they can fire on the wrong file type | `paths:` is read and ignored: a skill declaring `paths: ["**/*.toml"]` is listed identically in a host with a `.toml` file and in one with none [L10] |
| `user-invocable: false` | ignored, same as above. `disable-model-invocation: true` does not remove a skill from the listing either: a skill declaring both is listed `enabled: true` next to an ordinary one [L11] | the frontmatter is parsed and the flags are not honoured. There is no copilot equivalent of "model-invocable only" |
| An agent's `tools:` list | not enforced. An agent declaring `tools: Read, Grep` overwrote a file when asked to, exactly as an agent declaring `tools: Read, Grep, Write, Edit` did [L12] | the kit's 11 agents are therefore *not* least-privilege here. The hook gate is what stops a bad call, and it works [L5]; the tool list is documentation. A host that needs the restriction has to deny it in `copilot` permissions |
| `!` shell injection in a command | not expanded. A command body holding `` !`echo $((6*7))` `` reached the model as the literal text with the dollar sign and the parentheses, and it read the command file as a file to see that [L13] | a documented Claude feature with no copilot equivalent found. A kit command that leans on it must be rewritten for the host; `commands/prompt.md` and the workflows are the ones to check |
| The post-edit gate | fires but does nothing. The `PostToolUse` hook is delivered, and copilot's `tool_input` is a **patch string**, not an object: `"tool_input": "*** Begin Patch\n*** Add File: x.py\n+x=1\n*** End Patch\n"`. `hooks/scripts/gates.py` reads `tool_input.file_path`, which raises, which `hooks.py` swallows as its documented fail-open, so a gate failure is indistinguishable from a clean file [L14] | a host that wants the gate needs a copilot-aware path extractor. It is not generated here because the fix belongs in `gates.py`, which every harness shares, not in one harness's export |
| An agent's `model:` line | accepted and ignored. The kit's agents carry `model: opus` and `model: sonnet`, which mean nothing to copilot | copilot picks the model. Nothing is written into any generated file: a model identifier in a dist is a claim about a host the kit does not own |
| `bin/` on the agent's `PATH` | not on it. A fixture plugin shipping a one-line executable under its own `bin/` did not resolve it: the agent ran `command -v <name>` and got exit 1 [L15] | every `devil <tool>` call from a copilot session needs the absolute path or a `cd` into the kit. This is the same cell the OpenCode bridge had to solve, and there it was solved with a plugin shell hook; copilot has no equivalent channel |
| A plugin cannot ship instructions | the always-on rules cannot travel inside the plugin at all | `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md` and `.github/instructions/x.instructions.md` were each placed at a plugin root in turn and `copilot instruction list` reported `No instruction sources found` every time [L16]. Hence the copy step in the install section |

## What is not supported

- **`applyTo:` as lazy loading. It is not lazy loading.** Every
  `.github/instructions/*.instructions.md` in a host is listed in the prompt whatever
  its pattern: a file declaring `applyTo: "**/*.nomatch"` still got a row, and so did
  `**/*.py` in a host with no Python file [L17]. What the pattern changes is only the
  *form*: `**` and `**/*` get the body inlined, and anything narrower gets a pointer
  row in a table the prompt tells the model to read with a file tool [L18]. A kit rule
  delivered this way is delivered either way, so generating the 7 rule skills as
  `*.instructions.md` would buy nothing and cost 7 files. That is why none are
  generated, and it corrects the plan's example.
- **`templates/mcp.json`.** copilot reads `mcp.json` (portable), `.mcp.json` or
  `.github/mcp.json` from a *host*; a plugin's MCP is configured in the manifest and the
  kit has none to ship, because a plugin MCP would start the server for every installer.
  Not generated.
- **`.claude/CLAUDE.md`.** It is not an instruction source in 1.0.89. A host with
  nothing but `.claude/CLAUDE.md` gets `No instruction sources found` [L19]. This
  corrects the matrix cell that listed it: the kit's own Claude Code instructions are
  invisible to a copilot session in the same repository.
- **The 29 hook events with no copilot equivalent.** copilot's set is Claude's plus
  `permissionRequest`, `postToolUseFailure` and `preCompact`. The generated
  `hooks.json` keeps all 30 declarations, because a declaration for an event the host
  does not have is inert rather than harmful; what actually runs is
  `PreToolUse`, `PostToolUse` and `SessionStart` [L5][L6][L14].
- **A hook that needs `args`.** The array is not read [L8], so a hook that separates an
  executable from its arguments cannot be expressed. The generated file collapses each
  one into a single shell line, which works and is quoted; it is not a general
  translation of the Claude shape.
- **Attribution of a commit, a push or a deploy**, which stays a human action whatever
  the harness. The hook gate enforces only what `hooks/scripts/risk.py` enforces.

## Verifying an install

```sh
copilot --plugin-dir "$DIST" skill list --json | jq -r '.[] | select(.source=="plugin") | .name'
copilot --plugin-dir "$DIST" --agent nosuch -p hi 2>&1 | head -1
copilot --plugin-dir "$DIST" instruction list
```

Three answers in order: the kit's 25 skills are advertised, the 11 agents are namespaced
`devil:<name>`, and the host's `.github/copilot-instructions.md` is listed as a
repository instruction. Then the deny path, which is the one that matters:

```sh
cd "$HOST" && copilot --plugin-dir "$DIST" --allow-all-tools \
  -p 'Run exactly this shell command and nothing else: git push --force origin main'
```

The force-push must be refused with the kit's own wording, not with a copilot message
about permissions. If it is refused by copilot's own permission system, the hook never
ran and the gate is not installed.
