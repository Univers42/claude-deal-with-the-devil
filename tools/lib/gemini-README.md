# The kit on Gemini CLI

`dist/gemini/` is a Gemini CLI extension, generated by `devil export gemini` from the kit's
Claude-format sources. Never edit it: `bash tools/export.sh --check gemini` regenerates into a
temp directory and fails on any difference, and CI runs it.

Everything claimed below was measured against **0.62.0** (npm `@google/gemini-cli`, the current
`latest`) in a throwaway container on 2026-09-30, with the command and its output line recorded in
`doc/HARNESSES.md`, section "Gemini CLI, measured for X3".

## Install

```sh
KIT=/path/to/claude-deal-with-the-devil
gemini extensions install "$KIT/dist/gemini"
```

`install` copies the directory, so an edit in the kit is not seen until you re-install.
`gemini extensions link "$KIT/dist/gemini"` symlinks it instead and does see them; use the
symlink while working on the kit and the copy for a real install.

Two things to know before the first run:

- **The CLI needs an auth method configured even for local commands.** `gemini extensions list`
  refuses with "Please set an Auth method ... or specify one of ... `GEMINI_API_KEY`,
  `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_GENAI_USE_GCA`" before it does anything, and a prompt asks
  whether to trust the workspace. `--skip-trust` skips the second; the first is your own login.
- **Extension commands have the lowest precedence.** A command name that already exists in the host
  gets prefixed with the extension name, so `/devil.deal` rather than `/deal`. That is the one
  place the kit is namespaced by accident rather than by the plugin rules.

## What works

Each row names the measurement behind it. A row with no measurement is in one of the two tables
below instead, marked UNVERIFIED, because an unmeasured claim is a hope.

| Kit asset | On Gemini CLI | How, and what proved it |
| --- | --- | --- |
| The manifest itself | full | `gemini extensions validate dist/gemini` printed `Extension ... has been successfully validated.` |
| Commands | full | `commands/<name>.toml` with `description` and `prompt`, the documented v1 format. `gemini extensions validate` accepts the file; the prompt reaching the model is UNVERIFIED, since that needs a session |
| Skills | full | `skills/<id>/SKILL.md` copied verbatim. The loader reads only `name` and `description` and ignores every other frontmatter key, so `allowed-tools` and `metadata` cost nothing and are not misread |
| Sub-agents | full, with a caveat on the schema | `agents/<name>.md` carrying only `name`, `description`, `kind` and `tools`. The loader's schema is `.strict()`, so `model:` and `memory:` are dropped: an unknown key fails the file, it does not warn |
| Tool restrictions on an agent | full, deny by default | a Claude `tools:` list becomes a Gemini allow list. An agent with no recognisable grant gets `tools: []`, which is truthy in JS and so means none, where an omitted key would inherit every tool |
| Always-on rules | full | the manifest's `contextFileName` points at `DEVIL.md`, the 12 rules concatenated. The validator fails when a named context file is missing, so a broken reference cannot ship |
| Deny a catastrophic command | translation proved, firing UNVERIFIED | `gemini-hook.py` in this directory turns `BeforeTool` + `run_shell_command` into `PreToolUse` + `Bash` and returns `{"decision": "deny", "reason": ...}`. `tests/test_export_gemini.sh` asserts that on a force-push payload. Whether the CLI fires the hook is not run here |
| Ask on the irreversible | translation proved, firing UNVERIFIED | the same payload path, returning `{"decision": "ask", ...}`, which the CLI's own `isAskDecision()` reads as ask |
| The post-edit gate on a new file | translation proved, firing UNVERIFIED | `AfterTool` + `write_file` becomes `PostToolUse` + `Write`, and the file path is lifted from the same four keys the CLI's own path extractor probes |
| Facts before compaction | translation proved, firing UNVERIFIED | `PreCompress` becomes `PreCompact`, and the note is text, so nothing else has to work |

## What is degraded

| Gap | Consequence | Why it cannot be fixed here |
| --- | --- | --- |
| The post-edit gate never runs on an edit | `replace`, Gemini's edit tool, has no path parameter: its parameters are `instruction`, `old_string`, `new_string`, `allow_multiple`. Only `write_file` reports a file, so shellcheck and ruff run on files the agent creates and not on files it modifies | measured in the 0.62.0 bundle (`EDIT_PARAM_*`). There is no path to gate. `tools` in the extension is the place to add a host-side gate |
| No path-scoped rules | the 7 `stage: rule` skills (`refactor-c`, `refactor-go`, `refactor-rust`, `refactor-typescript`, `refactor-shell`, `api-convention`, `script-library`) ship as ordinary skills and load whenever the model picks them | no glob field in Gemini skill frontmatter; the loader keeps only `name` and `description`. The nearest equivalent is a `GEMINI.md` in the subtree, which is host-owned |
| No session briefing | `SessionStart` fires and returns nothing | the briefing is `tools/digest.sh`, and `tools/` is not in this extension. Copying the tools here would ship a second copy of the kit's scripts for one hook |
| No re-check of the kit's own docs after an edit | the post-edit hook's kit-doc branch never fires | it needs `tools/selfcheck.sh` and `tools/skillcheck.sh` under the extension root, same reason |
| `bin/devil` is not on the agent's PATH | a command body that says `devil <tool>` needs an absolute path or `${extensionPath}` | there is no shell hook to mutate the environment, and no PATH config key in an extension. This is the kit-wide per-harness accessor, listed in `doc/HARNESSES.md` |
| The extension manifest tolerates unknown keys | a stray key in `gemini-extension.json` is ignored, never reported | measured: a manifest carrying `bogusKey` validated clean. Only `name`, `version` and a resolvable `contextFileName` are actually checked |
| `gemini extensions validate` is shallow | it validates the manifest and nothing else | measured: a `commands/*.toml` with no `prompt`, a `SKILL.md` with no frontmatter at all, and a `hooks.json` full of Claude event names all validated clean. A green validate is not a green extension |
| Hook timeouts are milliseconds | the kit's 5-second budgets became 5000, and anything copied from a Claude manifest without this restatement would be 5 ms | the CLI's schema documents milliseconds and a 60000 default; `gemini hooks migrate` copies the number across unchanged, which is a trap |

## What is not supported

- **`hooks/hooks.json` file for file.** Gemini has nine event names, the kit's manifest declares
  twenty-nine, and five of the kit's enforcers have a Gemini equivalent at most. Only
  `BeforeTool`, `AfterTool`, `SessionStart` and `PreCompress` are generated, because only those
  four have a Claude counterpart that does something. The other twenty-five are unreachable, and
  the notification sounds never fire here.
- **`args` on a hook.** Gemini's hook is a shell command string with no `args` array, which is why
  the generated command names the interpreter and `gemini-hook.py` in full, under
  `${extensionPath}`. `gemini hooks migrate` silently drops `args` when it converts a Claude
  file, so a hook that relied on one becomes a command that names only its interpreter.
- **`{{args}}` inside `!{...}`.** The docs say arguments inside a shell block are shell-escaped,
  but the kit's commands are written for Claude's raw `$ARGUMENTS` substitution, and a command
  that has no `!{...}` block is unaffected. Any command body that does use one needs a second look
  before it is trusted here.
- **`templates/mcp.json`.** An extension declares `mcpServers` in its own manifest. Not
  generated: the kit's MCP server is the user's choice, and shipping it would start a server for
  every host that installs the extension.
- **No model, no provider, no variant.** The kit's agents carry `model: opus` and `sonnet`. Those
  names are dropped, not translated: the right model is the host's choice and a generated file
  must not name one.
- **Attribution of a commit, a push or a deploy**, which stays a human action whatever the
  harness. The hook enforces only what `hooks/scripts/risk.py` enforces.

## Verifying an install

```sh
gemini extensions list                 # devil is listed, with its version
gemini extensions validate dist/gemini # the manifest still passes
```

`validate` proves the manifest and the context file, nothing else. To see a hook run, ask the
agent to run a force-push and read the refusal; the CLI's own hook metrics
(`GEMINI_CLI_HOOK_EVENT_NAME`, `GEMINI_CLI_HOOK_EXIT_CODE`, `GEMINI_CLI_HOOK_SUCCESS`) are what
telemetry reports, and a hook that does not appear there did not run.

Neither was run here: it needs an account, and `doc/HARNESSES.md` records that as not run rather
than as a pass.
