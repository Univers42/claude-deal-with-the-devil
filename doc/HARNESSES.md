# Harness facts

What each agent harness can actually read from this kit, verified 2026-09-30. Every cell
in the matrix carries a footnote: `[n]` is a documentation page, `[Ln]` is a local run on
this machine. A cell with no footnote is **UNVERIFIED** and must not be relied on.

Read this before designing the exporter (slice X1). The canonical sources stay the Claude-format
files (`skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `rules/`); a harness that
reads those natively needs nothing generated, and a harness that does not needs a
generated dialect. Nothing here is generated by the kit yet: this file is the evidence X1
to X4 build on.

Versions measured here: Claude Code 2.1.285, OpenCode 2.0.18, GitHub Copilot CLI 1.0.59.
Gemini CLI and Codex CLI are **not installed**, so those two columns are documentation-only.

## Footnotes: local runs

Scratch project `target/probe/oc`, a git repo holding `.opencode/{agents,commands,skills,plugins}`,
`.claude/{skills,agents}`, `AGENTS.md`, and an `opencode.json`. Copilot runs used
`COPILOT_HOME=target/probe/copilot-home`; nothing under `$HOME` was written except
`~/.cache/copilot/marketplaces/`, which the CLI itself created during [L9].

- **L1** `opencode run --standalone --auto -m 'opencode/space-bunny-free#max' --agent build "<list skills, subagents, was an instruction file loaded>"`, from `target/probe/oc`.
  Output lines: the skill list contains both `probeskill` (from `.opencode/skills`) and
  `probeskill2` (from `.claude/skills`); the subagent list is `explore, general, probeagent`
  and does **not** contain `probeagent2` from `.claude/agents`; the AGENTS.md answer is `yes`.
  So `.claude/skills` is read, `.claude/agents` is not, `AGENTS.md` is.
- **L2** Same runner with the prompt `/probecmd`, where `.opencode/commands/probecmd.md`
  holds a `` !`echo PROBE_INJ_$(od -An -N2 -tu2 /dev/urandom ...)` `` block. The model
  answered: "the `!` backtick shell expansion is a Claude Code feature and wasn't executed".
  `opencode run` does not expand a command template or run its shell block; command
  registration in the TUI is documented [5] but was not exercised.
- **L3** Negative control for the deny probe, same runner with
  `Run exactly this bash command ... echo DEVIL_PROBE_DENY` and no plugin present.
  Output line: `echo DEVIL_PROBE_DENY` then `DEVIL_PROBE_DENY`. The command ran.
- **L4** `.opencode/plugins/devilprobe-v2.js`, a default export with `id` and `setup(ctx)`
  that registers `ctx.tool.hook("execute.before")` and throws when the command contains
  `DEVIL_PROBE_DENY`. Same prompt as [L3]. Output line:
  `Error: DEVIL_PROBE_DENY refused by the probe plugin (v2 tool hook)`, tool result
  `{"error":{"type":"unknown","message":"DEVIL_PROBE_DENY refused by the probe plugin (v2 tool hook)"}}`.
- **L5** `.opencode/plugins/devilprobe-perm.js`, same shape but registering
  `ctx.permission.hook("evaluate")` and setting `event.effect = "deny"` plus a message.
  Output line: `Error: DEVIL_PROBE_PERM refused by the probe permission hook`.
  Both mechanisms deny; the permission hook is the closer analogue of `PreToolUse`.
- **L6** `opencode serve --port 7790`, then
  `curl -u opencode:<password from the serve log> "http://127.0.0.1:7790/api/config"`.
  The response lists `.../X0/opencode.json` and shows its V1 `permission` object rewritten
  into the V2 `permissions` array. A project `opencode.json` is also read by walking up from
  the working directory, so a kit `opencode.json` at a repository root reaches every
  subdirectory, including worktrees.
- **L7** `COPILOT_HOME=target/probe/copilot-home copilot plugin install ./fake-claude-plugin`,

## Share as-is, or generate

**OpenCode.** Share `SKILL.md` files by pointing `skills` at the kit's `skills/` directory
[2]: one config entry replaces a copy per project. Generate agents (`.opencode/agents/*.md`
with `mode: subagent` and a `permissions:` list [4]), commands (`.opencode/commands/`,
`$ARGUMENTS` [5]), a plugin that bridges hooks [8], and any always-on text as `AGENTS.md`
[3]. Never ship `CLAUDE.md` for OpenCode; V2 ignores it [3]. Path-scoped rules have no
equivalent: the closest is an `AGENTS.md` inside the subtree, which loads when the agent
reads a file under it [3].

**Copilot CLI.** The most shareable harness: it reads `.claude-plugin/plugin.json` [L7],
`.claude/skills`, `.claude/agents`, `.claude/commands` and `.claude/settings.json` hooks
[11][13][14][15]. Generate only the pieces whose dialect differs: plugin agents as
`*.agent.md`, plugin hooks as `hooks.json` with `bash` or `exec` plus `args` [11][13], and
`*.instructions.md` files with `applyTo:` for path-scoped rules [14]. Two things to check
before trusting them: whether `${CLAUDE_PLUGIN_ROOT}` expands inside a hook `bash` string
(documented for MCP, LSP and agent `mcp-servers`, silent for hooks [11]), and whether a
`.claude/agents/*.md` file without the `.agent.md` suffix is picked up [11][16].

**Gemini CLI.** Nothing is shared but the file bodies. Generate `gemini-extension.json`
[20], commands as TOML with `{{args}}` and `!{...}` [22], hooks in `hooks/hooks.json` with
`BeforeTool` instead of `PreToolUse` and a regex matcher [21], and `${extensionPath}` in
place of `${CLAUDE_PLUGIN_ROOT}` [20]. Skills can be copied verbatim into `skills/` [20][29].
Agents in an extension are a preview feature [20].

**Codex CLI.** The hook payload is nearly Claude's, so `hooks/hooks.json` and
`hooks/scripts/hooks.py` are close to reusable: the events are Claude's, `matcher` is a
regex that accepts `Bash`, the deny shape is `hookSpecificOutput.permissionDecision: "deny"`
or exit 2, and `timeout` is in seconds [24]. Generate `.codex-plugin/plugin.json` (or a
root portable `plugin.json` plus `mcp.json`) [28], agents as TOML under `.codex/agents/`
[27], and `AGENTS.md` for always-on text [25]. Codex skills come from `.agents/skills`, not
`.claude/skills` [26], so either a symlink or a copy is needed.

**Claude Code.** The source format. Nothing generated.

## Proposed layout for generated files

Generated trees live under `dist/<harness>/` and are never edited by hand. Keeping them
out of the plugin root means no harness reads them by accident, and the plugin root keeps
its Claude-only `commands/`, `agents/`, `skills/`, `rules/` names.

```text
dist/
├── opencode/
│   ├── opencode.json          # skills paths pointing at ../../skills
│   ├── .opencode/agents/<name>.md
│   ├── .opencode/commands/<name>.md
│   ├── .opencode/plugins/devil.js
│   └── AGENTS.md
├── copilot/
│   ├── plugin.json            # Agent Plugins 1.0 if adopted, else legacy
│   ├── agents/<name>.agent.md
│   ├── commands/<name>.md
│   ├── hooks.json
│   └── .github/instructions/<name>.instructions.md
├── gemini/
│   ├── gemini-extension.json
│   ├── commands/<name>.toml
│   ├── hooks/hooks.json
│   └── skills/<name>/SKILL.md
└── codex/
    ├── .codex-plugin/plugin.json
    ├── .codex/agents/<name>.toml
    ├── hooks/hooks.json
    └── mcp.json
```

One layout decision worth recording now: Agent Plugins 1.0 is the same portable format in
Copilot CLI [10][11] and Codex [28], and its three files are `plugin.json`, `skills/`,
`mcp.json`. Emitting that as the Copilot and Codex target would make the skills and MCP
config shared rather than generated twice. Gemini CLI cannot read it, and OpenCode has no
plugin concept at all, so it stays out of the plan until X2 and X4 confirm it.
