# Harness facts

What each agent harness can actually read from this kit, verified 2026-09-30. Every cell
in the matrix carries a footnote: `[n]` is a documentation page, `[Ln]` is a local run on
this machine. A cell with no footnote is **UNVERIFIED** and must not be relied on.

Read this before designing the exporter (slice X1). The canonical sources stay the Claude-format
files (`skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `rules/`); a harness that
reads those natively needs nothing generated, and a harness that does not needs a
generated dialect. Nothing here is generated by the kit yet: this file is the evidence X1
to X4 build on.

Versions measured here: Claude Code 2.1.285, OpenCode 2.0.18, GitHub Copilot CLI 1.0.59.
The Gemini CLI column was documentation-only until slice X3, which measured 0.62.0 in a
container; see "Gemini CLI, measured for X3" for what was run and what was not. Codex CLI is
still **not installed**, so that column is documentation-only.

## Share as-is, or generate

**OpenCode.** Share `SKILL.md` files by pointing `skills` at the kit's `skills/` directory
[2]: one config entry replaces a copy per project. Generate agents (`.opencode/agents/*.md`
with `mode: subagent` and a `permissions:` list [4]), commands (`.opencode/commands/`,
`$ARGUMENTS` [5]), a plugin that bridges hooks [8], and any always-on text as `AGENTS.md`
[3]. Never ship `CLAUDE.md` for OpenCode; V2 ignores it [3]. Path-scoped rules have no
equivalent: the closest is an `AGENTS.md` inside the subtree, which loads when the agent
reads a file under it [3].

**Copilot CLI.** The most shareable harness: it reads `.claude-plugin/plugin.json` [L7],
`.claude/skills`, `.claude/agents`, `.claude/commands` and `.claude/settings.json` hooks
[11][13][14][15]. Generate only the pieces whose dialect differs: plugin agents as
`*.agent.md`, plugin hooks as `hooks.json` with `bash` or `exec` plus `args` [11][13], and
`*.instructions.md` files with `applyTo:` for path-scoped rules [14]. Two things to check
before trusting them: whether `${CLAUDE_PLUGIN_ROOT}` expands inside a hook `bash` string
(documented for MCP, LSP and agent `mcp-servers`, silent for hooks [11]), and whether a
`.claude/agents/*.md` file without the `.agent.md` suffix is picked up [11][16].

**Gemini CLI.** Nothing is shared but the file bodies. Generate `gemini-extension.json`
[20], commands as TOML with `{{args}}` and `!{...}` [22], hooks in `hooks/hooks.json` with
`BeforeTool` instead of `PreToolUse` and a regex matcher [21], and `${extensionPath}` in
place of `${CLAUDE_PLUGIN_ROOT}` [20]. Skills can be copied verbatim into `skills/` [20][29].
Agents in an extension are a preview feature [20]. Both of the last two sentences survived
measurement and one of them sharpened: a sub-agent's frontmatter schema is `.strict()`, so
verbatim is not an option there and only the four accepted keys may be emitted [L26].

**Codex CLI.** The hook payload is nearly Claude's, so `hooks/hooks.json` and
`hooks/scripts/hooks.py` are close to reusable: the events are Claude's, `matcher` is a
regex that accepts `Bash`, the deny shape is `hookSpecificOutput.permissionDecision: "deny"`
or exit 2, and `timeout` is in seconds [24]. Generate `.codex-plugin/plugin.json` (or a
root portable `plugin.json` plus `mcp.json`) [28], agents as TOML under `.codex/agents/`
[27], and `AGENTS.md` for always-on text [25]. Codex skills come from `.agents/skills`, not
`.claude/skills` [26], so either a symlink or a copy is needed.

**Claude Code.** The source format. Nothing generated.

out of the plugin root means no harness reads them by accident, and the plugin root keeps
its Claude-only `commands/`, `agents/`, `skills/`, `rules/` names.

├── opencode/
│   ├── opencode.json          # skills paths pointing at ../../skills
│   ├── .opencode/agents/<name>.md
│   ├── .opencode/commands/<name>.md
│   ├── .opencode/plugins/devil.js
│   └── AGENTS.md
├── copilot/
│   ├── plugin.json            # Agent Plugins 1.0 if adopted, else legacy
│   ├── agents/<name>.agent.md
│   ├── commands/<name>.md

│   ├── hooks/hooks.json
│   └── skills/<name>/SKILL.md
└── codex/
    ├── .codex-plugin/plugin.json
    ├── .codex/agents/<name>.toml
    ├── hooks/hooks.json
    └── mcp.json

## OpenCode, measured for X1

Everything below was run on this machine against OpenCode **2.0.18** on 2026-09-30,
after [L1]-[L5] left four questions open. Scratch hosts lived under `target/probe/x1/`
(inside the kit, so the project root was the kit) and `/tmp/opencode/x1proof` (outside
it, so the kit's own `opencode.json` was not in the config chain). The difference
between those two hosts turned out to matter and is recorded as **[L13]**.

Unless stated otherwise each run was
`opencode run --standalone --auto -m 'opencode/space-bunny-free#max' --agent build "<prompt>"`.

**How a plugin must be written.** Three facts, all measured, that no documentation page
states and that together make a correct plugin a no-op:

- **`setup` must be synchronous.** An `async setup` that awaits its registrations leaves
  every hook registered but never fired [L12]. A `setup` that lets a transform throw
  behaves the same way: the registrations made before the throw do not take effect.
- **A registration that resolves is not a registration that applied.**
  `ctx.skill.transform` resolves cleanly and `editor.add` never reaches the registry [L12].
- **There is no API that adds an agent.** `AgentEditor` exposes `list`, `get`, `default`,
  `update`, `remove` and no `add`, so agents must be files. Commands, by contrast, are
  added by a plugin: `ctx.command.transform(editor => editor.add({...}))` puts the command
  in `ctx.command.list()` immediately [L12].

**Q1a: can a plugin register agents, commands, skill directories or instruction text?**
Partly, and the parts differ per domain.

| Domain | Programmatic registration | Measured |
|---|---|---|

**Q1c: how does a host load agents and commands from outside `.opencode/`?**

- **Agents and commands: only from `.opencode/<kind>/`**, i.e. a symlink into the host works
  and a copy works; nothing else does. A `agents` or `commands` key in `opencode.json` did

- **Skills: the `skills` config array works**, with an absolute path to a directory of

  refactor-rust, refactor-shell, refactor-typescript, caveat`.

  directory of `.js` files, and a directory carrying a `package.json` with `main` and
  `exports`; absolute and relative; with and without `--standalone`. `setup` never ran in any
  of the four, while the same file under `.opencode/plugins/` always ran. The symlink is
  the route that works.

**Q1d: what replaces always-on instructions in V2?** Not a config key: a plugin.

- The `instructions` array is accepted by the schema and resolves no file, glob or URL [3].
  This is the one cell [X0] got right from the documentation and it was re-confirmed.
- Two plugin channels reach the model, both measured with a unique marker [L16]:
  `ctx.session.hook("context", e => e.system.push({type:"text", text}))`, which runs on every
  model call of the agent loop, and `ctx.session.hook("prompt", e => e.prompt.text = ...)`,
  which runs once per user prompt. The answer to "is ZZMARKER_CTX present" was `yes` and
  to "is ZZMARKER_PROMPT present" was `yes`.
- `event.system` arrives with 4 entries and is a plain array; after the bridge's push it is
  6, the extra two being the 26,470 bytes of `rules/*.md` and the session briefing [L16].
  The model then quoted the heading of the injected rule document verbatim:
  `# Caveat — name what your heuristic gets wrong` [L17]. That is the proof the rules are
  really in the prompt and not merely pushed into an array nobody reads.

**The deny path, end to end.** `ctx.permission.hook("evaluate")` fires for every action,
including one the config already allowed, with `event.action = "shell"` and
`event.resources = ["<the raw command text>"]`. Setting `event.effect = "deny"` and
`event.message` blocks the call and the message reaches the model verbatim [L18]:

```text
Error: Refused: force-push to a protected branch. rules/risk.md treats this as a
one-way door with no bounded blast radius. If it is genuinely intended, run it
yourself — an agent should not be the one to do it.
```

That is `hooks/scripts/risk.py`'s own wording, unchanged, reached through the bridge.
Setting `effect = "ask"` prompts in a session; under `--auto` it is auto-approved, which is
what `--auto` means and is not a defect in the hook.

**The permission hook is offered one segment of a compound command.** This is the
sharpest edge found here and it is silent. [L21]

```text
enforce action=shell mapped=Bash resource="command -v devil"
```

That is the whole of what the permission hook saw for the call
`command -v devil; echo "exit=$?"; echo git push --force origin main`. The rest of the
string was never offered, the command ran, and nothing anywhere reported a gap. A
single-segment call is offered in full (`enforce action=shell mapped=Bash
resource="echo git push --force origin main"`, refused), so the split is invisible unless
you look for it. The bridge therefore checks a segmented command a second time in
`tool.execute.before`, which receives the whole string, and leaves single-segment commands
alone so ordinary work does not pay for a second `python3`.

- **L21** — the two runs above, same host, same prompt, one call each. Before the tool-hook
  backstop the segmented call printed all three statements; after it, the output line is
  `guardSegmented whole="command -v devil; echo \"exit=$?\"; echo git push --force origin
  main"` and the call is refused with `hooks.py`'s own wording. `tests/opencode-plugin-probe.mjs`
  pins the separator test and both halves of the behaviour.

**Tool names and input shapes**, from `tool.execute.before` [L19]: the tool is `shell`, not
`bash`; a write is `write` with input `{path, content}`; a read is `read` with `{path}`.
`execute.after` carries `status: "completed"` and the keys
`tool, sessionID, agent, messageID, id, input, status, result`. There is no field on it that
injects context, so a post-edit gate verdict is queued and delivered on the next
`session.context` call.

- **L13** — the same wiring, two hosts. `target/probe/x1/live` (project root = the kit repo)
  and `/tmp/opencode/x1proof` (project root = the host). A host inherits every
  `opencode.json` from its cwd up to the project root, so a host nested inside another
  repository inherits that repository's permissions: in `live`, a `git push` was refused by
  the *host's* `*git* push*: deny` rule with the bare message `Permission denied: shell`, and
  the bridge never got a vote, because an explicitly configured deny is final and does not
  invoke the hook [8]. Proof of a bridge denial has to run in a host whose config chain does
  not already answer `deny`.
- **L15** — the four `plugins` shapes above, plus `.opencode/plugins/probe6.js` in the same
  run to prove the file itself was sound. Output line: `registered tool.hook` never appeared
  for the config-path copies and did appear for the `.opencode/plugins/` copy.
- **L20** — the unterminated-frontmatter trap, which cost more experiments than anything
  else here. A generated agent whose `permissions:` block was not followed by a closing
  `---` produced this error and nothing else: `Error: Agent reviewer cannot run as a
  subagent`. The agent existed, its `description` was right, and `mode: subagent` had been
  dropped because the block never closed. Proof it is the fence and nothing else: deleting
  the closing `---` from one working agent reproduces it, and a YAML parse of the same file
  reports the frontmatter as unterminated. `tests/test_export.sh` now parses every generated
  frontmatter with PyYAML and fails on exactly this.

### What this changed in the matrix above

- **Hooks: deny a tool call** — `ctx.permission.hook("evaluate")` with `effect: "deny"` is the
  right mechanism for a hook that has to answer `PreToolUse`, because it is the only one that
  sees the raw command text. [L18]
- **`bin/` on the agent PATH** — **not no.** `ctx.shell.hook("create.before")` sets
  `event.env`, so a plugin can prepend its own `bin/` [L14]. The cell becomes `yes, via a
  plugin shell hook`.
- **Install** — `opencode plugin add` installs an npm or git package. A local checkout is
  **not** reachable through the `plugins` config array in 2.0.18 [L15]; the working install
  is a symlink into `.opencode/plugins/` plus a symlink per asset directory, which is what
  `dist/opencode/README.md` now specifies.
- **Plugin-root variable** — `ctx.location.directory` is the **project** directory for a
  plugin under `.opencode/plugins/`, not the plugin's own directory, so it cannot locate the
  kit. `import.meta.url` can, and that is what the bridge uses. `ctx.location.project.directory`
  is the git toplevel and is the right value for `CLAUDE_PROJECT_DIR`; `.canonical` resolves
  to the **main** checkout and is wrong in a worktree, so the bridge does not use it [L16].
- **Agents** — confirmed, with the unterminated-frontmatter trap attached [L20].
- **Path-scoped rule skills** — unchanged: no glob field in V2 skill frontmatter.
- **Hooks: inject context at session start** — `session.context` and `session.prompt` both
  work [L16]; there is no session-start event, so "once per session" is implemented by the
  bridge remembering the session id.

## Gemini CLI, measured for X3

Measured 2026-09-30 against **`@google/gemini-cli` 0.62.0** (the current `latest` on npm),
installed into a throwaway `node:22-slim` image with `HOME` redirected to `/tmp/h`. The
commands are below so every row can be re-derived. Two of the methods need no account at
all; everything else does, and is recorded as not run rather than inferred.

**A naming note first.** `gemini` and `codex` are not on this machine's `PATH` ([L11] is
still true for both), which is why the measurement runs in a container. A hosted consumer
cannot have the kit's `bin/` on its agent's `PATH` either: only Claude Code and OpenCode can
([L14]), and for the other three every reference is an absolute path or a `${...ROOT}`
variable. `dist/gemini/README.md` says so rather than shipping a PATH recipe that does not
exist.

### What was run, and what came back

- **L22** — `docker run --rm -e HOME=/tmp/h node:22-slim bash -lc 'gemini --version'`,
  image built with `npm i -g @google/gemini-cli`. Output line: `0.62.0`.
  `gemini extensions --help` lists a subcommand the documentation pages do not mention:
  **`gemini extensions validate <path>`**. That is the whole offline oracle this slice has.
- **L23** — `gemini extensions validate <path>` on four hand-built manifests. Output lines,
  one per case:
  - `{"name":"e1","version":"1.0.0","description":"probe"}` → `Extension /work/e1 has been
    successfully validated.` (rc 0)
  - the same plus `"contextFileName":"devil.md"` and no such file → `The following context
    files referenced in gemini-extension.json are missing: devil.md` (rc 1)
  - `{"name":"e3","description":"no version"}` → `Invalid configuration in
    /work/e3/gemini-extension.json: missing "version"` (rc 1)
  - `{"name":"e_4",...}` → `Invalid extension name: "e_4". Only letters (a-z, A-Z), numbers
    (0-9), and dashes (-) are allowed.` (rc 1)

  So `version` is **required**, the name charset is enforced, and a `contextFileName` that
  does not resolve fails the manifest. A manifest carrying a completely unknown key
  (`bogusKey`, `keywords`) validated clean, so the schema is not strict and extra keys are
  ignored rather than reported.
- **L24** — the negative control for the validator, and its limit. One extension was built
  with all four components at once and validated: `commands/hello.toml` valid, a
  `commands/bad.toml` with **no `prompt`**, a `commands/extra.toml` with an unknown key, a
  `SKILL.md` with **no frontmatter at all**, a probe sub-agent markdown file, and a
  `hooks.json` full of **Claude event names** (`PreToolUse` with an `args` array). Every one
  of them returned
  `Extension ... has been successfully validated.` (rc 0).

  `gemini extensions validate` is a **manifest-only** check. A green validate says the name,
  the version and the context file are fine and nothing else. `tests/test_export_gemini.sh`
  therefore pairs the container check with a fixture manifest the CLI must reject, so its
  pass is not a pass by construction.
- **L25** — everything else needs an account, and the reason is worth recording precisely.
  `gemini extensions link`, `gemini extensions list` and `gemini skills list` all boot the
  full agent startup: each printed `[STARTUP] Phase 'cleanup_ops' was started but never
  ended` and then attempted a model call. With no auth method configured the refusal is
  `Please set an Auth method in /tmp/h/.gemini/settings.json or specify one of the following
  environment variables: GEMINI_API_KEY, GOOGLE_GENAI_USE_VERTEXAI, GOOGLE_GENAI_USE_GCA`
  (rc 41). With `GEMINI_API_KEY` set to a dummy value the first two print
  `[Routing] NumericalClassifierStrategy failed: ... "API_KEY_INVALID"` and exit 1. So **no
  install, no list, and no session was run on this machine.** The trust prompt is separate and
  happens first: `The current workspace at "/work" is not trusted. Do you want to trust this
  workspace to install extensions?` (rc 124 under `</dev/null`).

  What that leaves unmeasured is exactly the firing of a hook, which is the one thing this
  slice would most like to see. It is recorded here as not run, in the matrix, and in
  `dist/gemini/README.md` as UNVERIFIED on every enforcement row.
- **L26** — the shape of the dialect, read out of the installed bundle rather than inferred
  from a page. `cat bundle/*.js | tr '\n' ' '` then grep, on 0.62.0:
  - `EVENT_MAPPING`: `PreToolUse: "BeforeTool", PostToolUse: "AfterTool",
    UserPromptSubmit: "BeforeAgent", Stop: "AfterAgent", SubAgentStop: "AfterAgent",
    SessionStart: "SessionStart", SessionEnd: "SessionEnd", PreCompact: "PreCompress",
    Notification: "Notification"`. Nine event names for the kit's twenty-nine.
  - `TOOL_NAME_MAPPING`: `Edit: "replace", Bash: "run_shell_command", Read: "read_file",
    Write: "write_file", Glob: "glob", Grep: "grep", LS: "ls"`.
  - `migrateClaudeHook` keeps `command`, `type` and `timeout` and **drops `args`**, and it
    copies `timeout` across unchanged.
  - `RUN_SHELL` parameters: `SHELL_PARAM_COMMAND = "command"`. `EDIT_PARAM_*`:
    `instruction`, `old_string`, `new_string`, `allow_multiple` — **no path parameter at
    all**. The CLI's own path extractor is `args.file_path ?? args.path ?? args.filePath ??
    args.file`, which is the four keys the generated translator probes.
  - the agent loader: `loadSkillFromFile` returns `{name, description, location, body}` and
    ignores every other frontmatter key, while the sub-agent schema ends `.strict()` and
    keeps only `kind`, `name`, `description`, `tools`, `mcpServers`, `model`, `temperature`,
    `max_turns`, `timeout_mins`. `toolConfig: markdown.tools ? {tools: markdown.tools} :
    undefined`, so `tools: []` is an explicit empty allow list and an omitted `tools:` key
    **inherits every tool**. `nameSchema` is `/^[a-z0-9-_]+$/`.
  - the hook answer: `DefaultHookOutput` reads `decision` and `reason` at the **top level**,
    with `isBlockingDecision()` true for `block` or `deny` and `isAskDecision()` true for
    `ask`. `getAdditionalContext()` reads `hookSpecificOutput.additionalContext`, the same key
    Claude Code uses. The hook **input** payload does use `hook_event_name`, so only the
    event *values* and the tool names needed translating.
  - the extension's `hooks.json` is read as `JSON.parse(...)` and checked only for
    `typeof rawHooks.hooks === "object"`, so a top-level `description` next to `hooks` is
    ignored rather than rejected.

### What this changed in the matrix above

- **Skills** — `extension skills/<id>/SKILL.md`, and the loader reads only `name` and
  `description`. The cell's "standard set" was wrong in a way that helps: `allowed-tools` and
  `metadata` are inert, not rejected, so the copy is verbatim. [L26]
- **Skill frontmatter honoured** — narrower than "standard set": exactly two fields. [L26]
- **Commands** — `commands/*.toml` with `description` and `prompt`, nested path becomes
  `/a:b` [20][22], and `{{args}}` for arguments. Confirmed as v1 TOML. [L22]
- **Commands: shell injection** — `!{...}` with balanced braces, and a confirmation dialog
  before the command runs [22]. The kit's commands are written for Claude's raw
  `$ARGUMENTS`, and the generated TOML rewrites that to `{{args}}`; a body that also used a
  shell block would need a second look.
- **Agents** — `agents/*.md` in an extension is a **preview** feature [20], and the schema is
  **`.strict()`** [L26]. That is the load-bearing correction: a generated agent carrying the
  Claude `model:` or `memory:` keys would be rejected outright, silently, with no warning,
  rather than carried. The generator emits only the four keys it accepts.
- **Path-scoped rule skills** — unchanged: no glob field, the loader keeps two fields. The 7
  `stage: rule` skills ship as ordinary skills.
- **Hooks: deny a tool call** — the cell said `{"decision":"deny"}` on stdout [21]; the code
  agrees, and adds that `block` is also blocking, `ask` is a third value, and the reason is a
  sibling `reason` key rather than a nested one [L26].
- **Hooks: declaration** — `hooks/hooks.json` in the extension root, not in the manifest,
  and the file is parsed with a `typeof .hooks === "object"` check only, so unknown
  top-level keys are ignored [L20][L26].
- **Hooks: call an external script** — `type: "command"` with a **shell command string** and
  **no `args` array** [21][L26]. This is the correction with teeth: the CLI's own Claude
  migration drops `args`, so a hook that relied on one silently becomes a command naming only
  its interpreter. The generated file names the interpreter and the script in one string.
- **Hooks: event names** — nine names, confirmed as the reverse of the CLI's own map [L26].
- **Hooks: matcher** — a regex over the Gemini tool name, and the CLI ships the exact tool
  vocabulary a matcher has to be written against [L26].
- **Hook timeouts are milliseconds here and seconds in the Claude manifest** [21][L26]. The
  same `5` is 5 ms. `gemini hooks migrate` copies the number across unchanged, which is a
  trap rather than a conversion. The generated file restates the budgets (5000, 10000).
- **Plugin-root variable** — `${extensionPath}` in the manifest and in `hooks/hooks.json`,
  confirmed. `${workspacePath}` and `${/}` also exist [20].
- **Manifest** — `gemini-extension.json`, and `gemini extensions validate` is the gate. The
  cell did not say that `version` is required or that the name charset is enforced, and both
  fail the manifest [L23].
- **Versioning** — `version` in `gemini-extension.json`, `gemini extensions update`, and
  `gemini extensions link` for a symlinked checkout [20][22]. The generated manifest reads
  its version from `.claude-plugin/plugin.json` at export time, so one bump needs a re-run.
- **Install** — was "no, CLI not installed". Now: `gemini extensions validate` **ran** and
  accepted the generated extension [L24]; `install` and `list` were attempted and refused for
  want of an auth method [L25], so a real install is still **not run**.
- **Reads Claude Code formats natively** — unchanged and still nothing except `GEMINI.md` as a
  custom-instructions filename. The extension loader reads `skills/`, `commands/`, `agents/`
  and `hooks/hooks.json` from the extension root, and its own directories, not the Claude
  ones [L26].
