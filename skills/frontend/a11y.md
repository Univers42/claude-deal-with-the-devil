# Accessibility — the gate, not the polish

Loaded on demand by the `frontend` skill. `rules/quality-bar.md` layer 6 requires this;
this is what passing it means.

Inaccessible is not done. Most of what follows is also just correctness — a control with
no focus state is broken for anyone on a keyboard, which includes power users of your
own product.

## The five that catch most of it

1. **Semantic element before ARIA.** `<button>` over `<div role="button">`. The native
   element brings focus, keyboard, and the accessibility tree for free. The first rule
   of ARIA is not to use ARIA.
2. **Every input has a label.** A real `<label for>`, or `aria-label` when the design
   has no visible text. A placeholder is not a label — it disappears exactly when it is
   needed.
3. **Keyboard reaches everything.** Tab to every control, activate with Enter/Space,
   escape from every dialog and menu. Tab order follows visual order. No keyboard trap.
4. **Focus is visible.** Never `outline: none` without replacing it. `:focus-visible`
   for a ring that shows for keyboard and not on mouse click.
5. **Contrast passes.** 4.5:1 for body text, 3:1 for large text and for UI boundaries
   like input borders. Check it in **both** themes — dark mode fails this constantly.

## Images, motion, structure

- Every image has `alt`. Decorative ones get `alt=""` — omitting the attribute is not
  the same thing.
- One `<h1>`; headings descend without skipping. Screen-reader users navigate by them.
- Landmarks: `<main>`, `<nav>`, `<header>`, `<footer>`.
- Honour `prefers-reduced-motion` — reduce or remove non-essential animation.
- Never rely on colour alone. An error is an icon or text plus red, not red alone.
- `lang` on `<html>`, and on any element that switches language.

## Dynamic content

- A dialog traps focus while open, returns focus to the trigger on close, and closes on
  Escape.
- Async results that matter announce themselves: `aria-live="polite"` for a status,
  `assertive` only for something genuinely urgent.
- A validation error is tied to its field with `aria-describedby` and `aria-invalid`,
  and focus moves to the first invalid field on submit.
- A control whose state changes carries it: `aria-expanded`, `aria-pressed`,
  `aria-selected`.
- Loading state is announced, not only spun.

## Tools — each finds a different class

| Tool | Catches | Run as |
|---|---|---|
| `eslint-plugin-jsx-a11y` | static markup errors, at author time | part of lint, `--max-warnings 0` |
| `axe-core` / `@axe-core/playwright` | computed-DOM violations, contrast | in the test run, via `browser-testing` |
| Lighthouse a11y | a scored page-level pass | CI on key routes |

**Automated tools find roughly a third of real issues.** That is the honest number, and
it is why the manual pass below is not optional (`rules/ponytail.md`).

## The manual pass — five minutes, finds what tools cannot

1. **Unplug the mouse.** Complete the main task with the keyboard alone.
2. **Tab through.** Is focus always visible? Does the order make sense? Can you get out
   of everything?
3. **Zoom to 200%.** Does content reflow, or does it clip and scroll sideways?
4. **Both themes.** Re-check contrast in each.
5. **Turn on a screen reader** (VoiceOver `Cmd+F5`, NVDA, Orca) and listen to one flow.
   This is the step that reveals the unlabelled button.

## Report

State the tool and version, the findings, what was fixed, and **what is still failing**
— a skipped check is uncovered surface, never green (`rules/quality-bar.md`). Include
the manual-pass result explicitly; an automated-only pass is a partial one and should
say so.
